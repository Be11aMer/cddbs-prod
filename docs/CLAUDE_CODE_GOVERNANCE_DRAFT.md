## 5. Hooks Configuration

These hooks go into `.claude/settings.json` (project-level, shared) and `settings.local.json` (personal overrides).

### 5.1 Pre-Tool Quality Gate

Runs ruff lint before any file edit is confirmed, blocking the change if lint fails.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "if echo '$CLAUDE_TOOL_INPUT' | grep -q '\\.py\"'; then ruff check src/ tests/ --quiet; fi",
            "blocking": true,
            "description": "Lint gate: ruff check before Python file edits"
          }
        ]
      }
    ]
  }
}
```

> **Discussion**: This may be too aggressive in interactive editing (ruff runs on every edit). Alternative: run only on `PostToolUse` for Write operations, or only in pre-commit hook.

### 5.2 Dangerous Command Blocker

Blocks the most destructive git and shell operations before they execute.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 <repo-root>/scripts/claude_safety_gate.py '$CLAUDE_TOOL_INPUT'",
            "blocking": true,
            "description": "Block dangerous commands: force push, hard reset, DROP TABLE, rm -rf, --no-verify"
          }
        ]
      }
    ]
  }
}
```

**`scripts/claude_safety_gate.py`** (to be created) should block:
- `git push --force` / `git push -f` (to main or development)
- `git reset --hard` (without explicit user confirmation)
- `git clean -f` / `git checkout -- .`
- `DROP TABLE` / `TRUNCATE` (raw SQL in shell)
- `rm -rf` on project directories
- `--no-verify` on any git command (skips pre-commit hooks)
- `git commit --amend` on already-pushed commits

## 6. Rules by Domain

These rules should be added to CLAUDE.md under a `## Development Rules` section. They are structured for progressive disclosure — simpler rules first, constraint rules at the end.

### 6.1 Git Conventions

```
COMMIT FORMAT: type(scope): description (≤72 chars)
Types: feat | fix | test | docs | refactor | security | compliance | perf | chore
Scopes: api | pipeline | frontend | auth | scheduler | db | ci | collector | config

BRANCHING:
- Feature branches: feat/<sprint>-<short-description> (branch from development)
- Fix branches: fix/<issue-or-finding-id>-<short-description>
- Never branch from main directly
- PRs target development; only development merges to main

MERGE RULES:
- Squash commits are allowed for single-concern PRs
- Multi-concern PRs (e.g., feature + test + docs) keep individual commits
- DEVELOPER.md update must be in the same PR as the code change

DO NOT:
- git push --force to main or development
- git commit --amend on pushed commits
- git reset --hard without explicit user instruction
- --no-verify on any commit or push
```

### 6.2 Code Quality

```
PYTHON:
- ruff check src/ tests/ must pass before any PR (enforced in CI)
- Ignored rules (E501, E711, E712) remain ignored — do not add new ignores
- No bare except: clauses — always specify exception type
- No print() in pipeline code — use src/cddbs/utils/logger.py (logger.info/error)
- No TODO/FIXME in production code without a linked sprint ticket

TYPESCRIPT:
- No 'any' types — use proper TypeScript types or unknown
- All API response types defined in frontend/src/api.ts
- Components are functional (no class components)
- No inline styles — use MUI sx prop or theme

GENERAL:
- Functions do one thing; if a function needs a comment to explain what it does, split it
- No dead code left in merged PRs — remove or move to TODO_PHASE4 doc if intentionally deferred
- Magic numbers get a named constant
```

### 6.3 Security

```
PROMPT INJECTION:
- All user-supplied input through src/cddbs/utils/input_sanitizer.py before any Gemini call
- All external article content (SerpAPI, RSS, GDELT) must also be sanitised
  (use sanitize_text() from input_sanitizer.py)
- Structural markers required around untrusted content in prompts:
  [BEGIN UNTRUSTED ARTICLE DATA] ... [END UNTRUSTED ARTICLE DATA]

OUTPUT VALIDATION:
- Every Gemini JSON response must pass through output_validator.py before DB commit
- Validation errors are logged but do not crash the pipeline (lenient mode)
- Validation failures set analysis_status to "partial" or "failed"

AUTHENTICATION:
- Auth feature is toggled by CDDBS_API_KEY_ENABLED
- When adding new endpoints:
  - Read-only (GET) endpoints: may be public, document the decision
  - Write endpoints (POST/DELETE): must require X-API-Key when auth is enabled
  - Health check (GET /health) is always public — no exceptions

SSRF:
- Webhook URLs must pass through SSRF validation (blocks private IP ranges)
- No new outbound HTTP calls to user-supplied URLs without the same validation

SECRETS:
- API keys live only in environment variables (never in request schemas, DB, or logs)
- detect_secrets.py and secret-scan.yml are the enforcement mechanism

RATE LIMITING:
- All endpoints that trigger Gemini calls must have slowapi rate limits
- Default: 5/min for analysis endpoints, 3/min for topic runs
- 429 responses must include Retry-After header

DEPENDENCIES:
- No new runtime dependencies without: (a) pip-audit pass, (b) SBOM update review
- Dev dependencies go in a separate requirements-dev.txt (not yet created — create it)
```

### 6.4 Design Patterns

```
PIPELINE PATTERN:
- Pipeline modules live in src/cddbs/pipeline/
- Each module has a single entry-point function (e.g., run_sitrep_cycle(session))
- Gemini calls always go through genai_client.call_gemini() — never call SDK directly
- DB sessions are passed in as parameters, not created inside pipeline functions

API PATTERN:
- Endpoints are defined in src/cddbs/api/main.py
- Input validation via Pydantic models (not manual if/else checks)
- Background tasks for anything that takes >1 second (Gemini calls, pipeline runs)
- Status polling pattern: POST creates a job, GET /{id} polls status until completed

DB PATTERN:
- Schema changes use startup migrations in src/cddbs/database.py (add_column pattern)
- No Alembic migration files (startup migrations keep it simple for single-instance)
- New columns default to NULL-able to avoid breaking existing rows on deploy
- No raw SQL — use SQLAlchemy ORM only

SCHEDULER PATTERN:
- All scheduled jobs registered in src/cddbs/scheduler.py (CddbsScheduler)
- New jobs go through CddbsScheduler — never create background threads independently
- Job frequency controlled by env vars (CDDBS_*_INTERVAL_HOURS) with documented defaults

CONFIGURATION PATTERN:
- All config in src/cddbs/config.py as dataclass fields with defaults
- New env vars get a default value and a row in DEVELOPER.md Section 9
- Never hardcode URLs, model names, or thresholds in pipeline code
```

### 6.5 Testing

```
TEST REQUIREMENTS (mandatory for merged PRs):
- New pipeline module: ≥5 tests (happy path, error path, edge case, schema validation, integration)
- New API endpoint: ≥3 tests (success, 4xx error, auth-required when applicable)
- Security fix: regression test that would have caught the original bug
- Bug fix: one regression test minimum

TEST PATTERNS:
- Use conftest.py fixtures (db_session, client) — never create your own DB sessions in tests
- Mock all external APIs: @patch("src.cddbs.utils.genai_client.call_gemini")
- Test files import from src.cddbs — never import relative paths
- One assertion per test function (AAA pattern: Arrange, Act, Assert)
- Test names: test_<what>_<when>_<expected> (e.g., test_auth_missing_key_returns_401)

TEST CATEGORIES (separate files):
- test_<module>.py — unit tests for a module
- test_sprint<N>_<theme>.py — sprint acceptance criteria verification
- test_audit_<YYYY_MM>_<theme>.py — audit finding remediation verification

DO NOT:
- Make live Gemini or SerpAPI calls in tests (costs money + non-deterministic)
- Test implementation details — test behaviour and contracts
- Write tests that always pass regardless of the code (testing mocks not behaviour)
```

### 6.6 API Design

```
ENDPOINT CONVENTIONS:
- Resource URLs: /resource-name (kebab-case, plural for collections)
- Resource ID: /resource-name/{id} (integer or UUID)
- Actions on resources: /resource-name/{id}/action (e.g., /stats/source-credibility/refresh)
- List endpoints support pagination: ?limit=50&offset=0
- Response envelope: {data: [...], total: N} for lists; flat object for single resources

OPENAPI COMPLIANCE:
- All endpoints have Pydantic response_model — no Dict[str, Any] return types
- All required fields documented in Pydantic schemas
- Error responses: {"detail": "human-readable message"} (FastAPI standard)

EU AI ACT COMPLIANCE FOR AI-GENERATING ENDPOINTS:
- Endpoints that return Gemini-generated content must include ai_metadata in response:
  {model_id, prompt_version, quality_score, requires_human_review: true}
- See existing GET /analysis-runs/{id} as the reference pattern

AUTH BEHAVIOUR (when CDDBS_API_KEY_ENABLED=true):
- GET /health → always public
- GET /auth/status → always public
- POST /auth/provision → always public (creates key)
- All other routes → require X-API-Key header → 401 if missing/invalid
```

### 6.7 Database Migration

```
MIGRATION PATTERN (startup migration):
  # In src/cddbs/database.py, after existing migrations:
  with engine.connect() as conn:
      result = conn.execute(text(
          "SELECT column_name FROM information_schema.columns "
          "WHERE table_name='your_table' AND column_name='new_column'"
      ))
      if not result.fetchone():
          conn.execute(text(
              "ALTER TABLE your_table ADD COLUMN new_column VARCHAR(255)"
          ))
          conn.commit()

RULES:
- Always NULL-able on first deployment; add NOT NULL constraint in a later sprint
- Add column documentation to DEVELOPER.md Section 6 in same commit
- Test the migration with test_database.py (add a test that creates a row with the new column)
- Never rename or drop columns without a multi-sprint migration plan
  (rename: add new, migrate data, remove old — three separate sprints)
```

## 8. Progressive Disclosure Strategy

Progressive disclosure means Claude Code reveals complexity as needed, rather than dumping everything into every session. Here is how it maps to this project.

### Layer 1: Default Session Context (CLAUDE.md)

Every session loads CLAUDE.md automatically. It provides:
- Architecture at-a-glance
- Commands (make up, pytest, ruff)
- Key configuration table
- Phase 4 deferred work (do not implement without data)

**Rule**: CLAUDE.md stays lean. It is the session bootstrap, not the encyclopedia.

### Layer 2: Domain-Specific Agent Context

When work is clearly in one domain, spawn the relevant persona (Section 4 above). The persona prompt adds domain-specific constraints the base CLAUDE.md doesn't cover. This prevents, for example, the frontend engineer from changing startup migration patterns.

### Layer 3: Skill Invocation

For repetitive well-defined tasks (scaffold endpoint, write regression test, check compliance), invoke a skill. The skill encodes the institutional pattern so the user doesn't have to brief Claude on it each time.

**Principle**: A skill should be written once the same task has been done the same way three times.

### Layer 4: Reference Documentation

DEVELOPER.md, docs/RESOURCE_CONSTRAINTS.md, docs/SCHEDULING.md, and the compliance docs are consulted on demand — not loaded by default. Agents are pointed to specific sections as needed.

### Layer 5: Research Track

cddbs-research documents (sprint backlogs, retrospectives, compliance log, execution plan) are loaded only by the Researcher agent. Production agents do not read research artifacts.

### Interaction Pattern for Common Tasks

| Task | Approach |
|------|----------|
| Fix a bug in pipeline | Inline Claude (no agent needed) |
| Add a new API endpoint | Invoke `/api-design` skill → then Backend Engineer agent for implementation |
| Write tests for a new module | Invoke Test Writer agent |
| Review a PR | Invoke `/code-review` skill → Security Reviewer agent for security findings |
| Sprint planning | Invoke Researcher agent + `/sprint-plan` skill |
| Update DEVELOPER.md | Invoke `/docs-update` skill |
| Compliance impact assessment | Invoke `/compliance-check` skill |
| New feature security review | Invoke `/security-by-design` skill pre-implementation |
| Performance concern | Invoke Performance Reviewer agent |
| Auth enforcement check | Invoke `/auth-layer` skill |
